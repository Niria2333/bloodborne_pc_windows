# Windows 平稳 60 帧与帧时间验证

更新日期：2026-10-06。此页记录 Windows 适配的帧时间修复和单台电脑的短时测量；上游 Linux 性能数据另见原始文档。

## 使用方法

在 Windows 启动器选择“60 帧 · 推荐”，并勾选“全屏运行”“垂直同步”和“平稳 60 帧（120 Hz 全屏）”。画质、输出分辨率和超分预设仍由自己的图形设置决定；该选项不降低画质，也不生成插帧。

命令行的等效选择如下，游戏目录替换为自己的已解密 1.09 版目录：

```powershell
python .\run_windows.py --game "D:\Games\CUSA03023" --fps 60 --fullscreen --vsync --sync-refresh
```

`--no-sync-refresh` 或取消该勾选框恢复普通固定 60 帧配置。窗口模式、关闭垂直同步和其他帧率档位不启用此组合；勾选状态会保存，回到满足条件的选择后再次生效。此选项默认关闭，需要用户选择。

显示器必须在当前桌面分辨率下提供约 120 Hz 的全屏模式。运行时只匹配相同分辨率、刷新率与目标相差不超过 0.5 Hz 的模式，不为达到 120 Hz 降低桌面分辨率。不支持或切换失败时记录警告并保留/恢复桌面模式；动态时序和 60 FPS 限制仍生效，但不能据此认为实际显示刷新率已经变为 120 Hz。正常退出会恢复桌面显示模式，不修改全局显卡驱动设置。

## 修复内容

Windows 的普通 waitable timer 可能被合并到约 15.6 ms 的系统 tick。旧等待在 60 Hz 目标下曾出现约 31 ms 的长等待，随后又追赶提交，因此平滑后的 FPS 显示仍为 59～60，而转动镜头会感觉不连贯。

`Common::AccurateSleep` 现在优先创建高精度 Windows waitable timer；不支持时使用普通计时器，并检查创建、设置与等待结果。VideoOut 的帧提交 deadline 和内部 tick deadline 使用同一高精度等待，失败时回退到标准等待。修复无需默认启用性能日志。

“平稳 60 帧”组合将游戏时间推进与提交限帧分开：

| 设置 | 生效值与作用 |
| --- | --- |
| 保存的启动器档位 | `fps=60`，用户选择仍为 60 帧 |
| 游戏补丁 / `BB_FPS` | `uncap`，使用已有的动态游戏时序补丁 |
| `BB_FPS_LIMIT` | `60`，VideoOut 独立限制帧提交 |
| `BB_VBLANK_HZ` | `0`，使用已有的快速内部调度路径 |
| `BB_PRESENT_MODE` | `Fifo`，启用垂直同步 |
| `BB_FULLSCREEN_REFRESH_HZ` | `120`，请求当前桌面分辨率的全屏显示模式 |
| `BB_FRAMES_AHEAD` | `2`，允许两帧 GPU 管线缓冲 |

日志中的 `VideoOut: vblank 480 Hz, frame limit 60 FPS` 描述内部事件调度与限帧。**480 Hz 不是显示器刷新率，也不是游戏输出帧率。** 游戏目标保持 60 FPS；120 Hz 显示允许每帧占据两次刷新，约 16.67 ms。固定 160 Hz 显示的刷新间隔为 6.25 ms，60 FPS 在本次显示路径中常交替占用两次/三次刷新，即 12.5/18.75 ms。刷新节奏更匹配后仍可能出现 GPU 超预算、资源加载或着色器编译长帧。

## 同画质测量结果

硬件为 Windows 11、i5-13600KF、RTX 4070 Ti 12 GB、NVIDIA 驱动 617.14；游戏为 CUSA03023 1.09。输出 3840×2160、FSR 4 v07 INT8 Balanced，图形特效保持相同。测试使用复制存档，在同一区域预热后静止和按脚本转动镜头。PresentMon 显示路径均为 `Composed: Flip`；请求 SDL 全屏显示模式不等于本次采样获得了独立硬件 Flip。

对照的普通固定 60 帧已经包含高精度 Windows timer 修复。以下统计来自 PresentMon 显示时长，反映显示侧帧节奏：

| 预热后静止区间，55～65 秒 | 固定 60 帧，桌面 160 Hz | 平稳 60 帧，全屏 120 Hz |
| --- | ---: | ---: |
| 显示平均 FPS | 59.9945 | 60.0037 |
| 显示时长 p99 | 18.9607 ms | 16.7612 ms |
| 独立显示 1% Low | 39.97 FPS | 55.02 FPS |
| 显示时长超过 25 ms | 2 / 600 帧 | 1 / 600 帧 |
| GPU Busy 中位数 / p99 | 14.70 / 17.03 ms | 14.87 / 17.06 ms |

镜头运动区间为 72～110 秒，两组显示平均均约 60 FPS；固定 60 帧独立显示 1% Low 为 50.83 FPS，平稳 60 帧为 **58.20 FPS**，后者显示时长 p99 为 **16.7617 ms**。两次运动结束后的镜头朝向不同，静止区间是更直接的对照。

这里的独立 1% Low 先取最慢 `ceil(N × 0.01)` 帧的显示时长，求平均后用 `1000 / 平均毫秒` 得到 FPS；p99 使用 nearest-rank 分位数。p99 的倒数与最慢 1% 平均值的倒数是不同指标，一个孤立长帧就可能明显拉低后者。NVIDIA 浮窗 Low 的具体公式与采样窗口未知，这些结果不能保证复现浮窗数字，也不能保证每段游戏的 Low 都为 60。

最终部署后的真实启动器另进行了 120 秒短时运行，确认 FSR 4、4K 和上述环境组合生效。其静止/镜头区间原生 Present 调用开始间隔平均分别为 59.9994 / 60.0004 FPS、p99 为 17.4084 / 17.2371 ms，无间隔超过 25 ms。这是主机 API 提交行为验证，不是新的显示 1% Low 测量。另一次 20 秒运行使用 SDL 显示 API 检查：开始 3840×2160@159.98 Hz，游戏中 120 Hz，退出后恢复 159.98 Hz。

短时验证覆盖了 FSR 4 游戏内 4K 输出与帧时间改善。完整通关、长期 4K/60 FPS、全部场景和全部画质预设尚未验证；FSR 4.1.1 Windows 适配状态不因本次结果改变，见[验证记录](WINDOWS_VALIDATION.md)。

修复后完整运行 `build_windows.ps1 -Test`，**16/16 项 CTest、110/110 项 Python 测试**通过且无跳过；其中启动器 23 项、修改器 28 项。启动器新增回归覆盖平稳 60 帧组合、参数保存、重启和条件不满足时禁用。另行运行 **6/6 项 PresentMon 分析器测试**通过，验证独立 Low 与 p99 公式、时间单位/区间、交换链筛选、不可用显示时长和原生提交间隔。分析器测试不包含在构建脚本的 110 项中，使用合成 CSV，不执行游戏或代替上述实机测量。

## 可复用测量方法

1. 固定游戏版本、输出分辨率、超分预设和特效。用复制存档，分别运行普通固定 60 帧与平稳 60 帧；记录实际显示模式。关闭会改变测试负载的读回截图，先预热同一区域的着色器和资源。
2. 使用官方签名的 [PresentMon](https://github.com/GameTechDev/PresentMon) 对 `bb-probe.exe` 做有限时长采样。按该版本的帮助启用显示时长跟踪并输出 CSV；需要 ETW 管理权限时由用户通过 Windows UAC 授权。记录工具版本、时间列单位、PID、交换链和 PresentMode。
3. 在相同起点和路线采样；事先规定预热、静止和镜头区间，排除加载画面和截图读回。本次静止为第 55～65 秒，镜头运动为第 72～110 秒，均相对于首个选中进程样本。不能把其他采样的相同数字直接当成游戏启动后秒数。
4. 分别报告平均、p99、最慢 1% 平均取倒数、长帧数量与样本数。只分析同一 PID/交换链；不可把 CPU 调用间隔、GPU Busy 或平滑 FPS 当作已确认的显示时长。无法获得显示数据时明确指出，不能推断显示 Low。

仓库的 `scripts/analyze_presentmon.py` 支持 PresentMon CSV 与原生 Present API CSV。例如，采集的 `CPUStartTime` 单位为毫秒时：

```powershell
python .\scripts\analyze_presentmon.py .\out\capture.csv --time-unit milliseconds --after 55 --duration 10
python .\scripts\analyze_presentmon.py .\out\capture.csv --time-unit milliseconds --after 72 --duration 38
```

如果时间列使用秒，改用 `--time-unit seconds`；可用 `--pid` 与 `--swapchain` 指定目标。无指定交换链时工具选择匹配样本最多的一组，复测仍应核对其 PID 和交换链。PresentMon 的 `DisplayedTime` 是显示持续时长，单位毫秒，不是时间戳；`NA` 可能表示未显示或数据不可用，分析会另行计数而不是当作零毫秒。

可选 `BB_PRESENT_TIMES` 环境变量为主机 Present 调用写出诊断 CSV。常规启动器不设置此变量；诊断数据含提交间隔及 acquire/flush/互斥锁/Present 调用耗时，用于定位等待。其时间戳不能证明 GPU 已完成、屏幕已显示或帧是否丢弃。
